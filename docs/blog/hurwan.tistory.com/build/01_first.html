# 인증/인가
인터넷에서 사용자를 인증하는 기술은 굉장히 많습니다.

기본적으로 쿠키 방식이 존재하여 `sameSite`, `httpOnly`, `secure` 설정과 함께 인코딩 문자열을 넣음으로써 사용자의 정보를 확인할 수 있습니다. (`cors`: 다른 사이트에서 쿠키를 통해 데이터를 읽는 것을 브라우저가 막는 것, `csrf`: 다른 사이트가 쿠키를 사용하는 것을 서버에서 받아주지 않는 것의 설정 또한 중요합니다.)

이에 따라 서버에서는 미들웨어에서 `csrf` 설정, 쿠키 속 문자열 값 등을 확인한 후 사용자에게 올바른 서비스 또는 `401`/`403` 응답을 제공해주기도 합니다.

### Basic
`Basic` 방식은 굉장히 단순하고 쉽게 구현할 수 있는 방식입니다.

그냥 요청 헤더를 `Authorization: Basic Base64(user_id:password)`로 설정하여 발송하는 방식으로 보안에 취약하여 보통 사용하지 않습니다.

### Digest Authentication
`Digest` 인증 방식은 오래된 방식으로 권한이 필요한 접근의 경우, 서버가 클라이언트에 인증을 요청하게 됩니다. 이때 클라이언트는 HTTP 메시지의 헤더 속성 중 하나인 `Authorization`에 비밀번호를 알아야 만들 수 있는 해시값을 만들어 보내게 됩니다. 이 방식을 통해 서버가 해당 자원을 적절히 제공해주는 방식입니다.

예를 들어 다음과 같은 값이 들어가게 됩니다.
`Authorization: Digest username="hurwan", realm="my-site", nonce="abc123", uri="/admin", response="만들어진 해시값"`

> 하지만 해당 기술은 현재는 많이 사용되는 기술이 아닙니다. (구현이 복잡하고 HTTPS 없이는 안전하지 않아서)

### Bearer
`Bearer` 방식 또한 위와 비슷하게 `Authorization` 헤더에 토큰을 실어서 보내는 인증 방식입니다.

`Authorization: Bearer e3Gdewaafg4e35` 등과 같이 전달되게 됩니다.

`Bearer`는 *소유자*라는 뜻으로 해당 토큰을 가지고 온 요청은 인증된 사용자로 인정하겠다는 의미를 가지게 됩니다.

이는 `Digest`보다 간결하게 첫 로그인 이후 서버가 클라이언트에게 토큰을 발급해주면 이후에는 로그인 없이 요청마다 `Bearer` 토큰을 포함하여 요청을 보내게 되는 방식입니다.

> Bearer 또한 토큰이 탈취에 매우 취약하기 때문에 `HTTPS` 사용, `maxAge` 처리, 중요 작업 재인증 등의 기술을 사용합니다.
> Bearer는 토큰을 사용하는 특성상 JWT와 함께 사용되는 경우가 많습니다.

### JWT 토큰
JWT 토큰은 토큰에 사용자 정보와 검증용 서명이 들어있는 인증 토큰 형식을 말합니다.

이는 `JSON Web Token`의 약자로 `[Header].[Payload].[Signature]`과 같은 형태로 나누어져 있습니다.

- Header
> 헤더에는 해당 토큰의 서명 방식을 말합니다. `{ "alg": "HS256", "typ": "JWT" }`와 같은 형태를 취합니다. `alg`는 서명 알고리즘이며 `typ`는 토큰 타입을 의미합니다.
- Payload
> Payload는 실제로 개발자가 직접 설정하여 넣을 정보가 들어갑니다. 보통 사용자의 주요 정보는 들어가지 않으며 사용자의 ID, 역할, 만료 시간(`exp`), 발급자(`iss`), 발급 시간(`iat`), 토큰 주체(`sub`라는 고유 사용자 값. 보통 userId를 넣어서 만드는 것이 RFC 7519 표준)가 들어갑니다. 이러한 정보들은 보통 `claim`이라고 부릅니다.
- Signature
> Signature는 헤더와 페이로드를 비밀 키를 통해 해싱하는 방식입니다. 이를 통해서 공격자가 토큰을 위조하였는지 확인하는 CRC와 같은 역할을 하게 됩니다.

##### JWT의 특징
`JWT` 기술은 보통 `Stateless` 방식을 통해 서버에서 사용자의 상태(로그인 상태 등)를 알 필요가 없다고 합니다. 이를 통해 보통 `Stateless`라고 한다면 `JWT`가 주로 언급됩니다.

하지만 `Stateless`라고 해도 결국 로그아웃, 블랙리스트, `Refresh` 등을 위해서 캐시 서버 등에 저장하는 경우가 많기 때문에 이와 구별하여 판단할 필요가 있습니다.

**JWT의 Header와 Payload는 보통 Base64URL 인코딩이기 때문에 중요한 정보를 제공하면 안 되며 보통 해당 쿠키의 탈취에는 책임을 지지 않기도 합니다(서비스에서). 또는 HTTPS와 함께 잘 사용해야 합니다.**

### Authentication Header와 Cookie
위에서 설명한 `JWT`는 2가지 방식으로 클라이언트에서 저장 및 전송이 가능합니다.
1. 처음에 설명한 `Bearer`, `Basic`, `Digest` 등과 같은 `Authentication Header` 방식
2. `Cookie`를 통한 `key-value` 방식

이 중 `Authentication Header` 방식은 항상 클라이언트 측에서 명시적으로 헤더에 추가를 할 필요가 있어 보안 및 `CSRF` 공격을 방지할 수 있습니다. 하지만 이는 자바스크립트를 통해 접근이 가능한 점에 의한 `XSS` 공격이 가능한 점을 인지해야 합니다(공격자가 URL 등을 통해 악성 `js`를 심는 방식을 통해 이루어질 수 있습니다). `Cookie`의 경우에는 보안 옵션을 통해 `XSS`를 방지할 수 있지만 반대로 `CSRF`의 위험이 존재합니다(`SameSite`를 활성화하더라도 리다이렉트, GET 요청, 서브도메인 등에 의해 발생할 수 있는 취약점이 존재합니다).

### 세션 ID
세션 ID 방식은 사용자가 로그인하면 일정 시간 동안 사용자가 로그인했다는 정보를 서버에 저장해놓은 뒤, 사용자에게 세션 ID를 토큰처럼 발급해주는 방식입니다. 예를 들어 `java Tomcat`의 경우에는 `JSESSIONID`를 주는 것을 확인할 수 있습니다.

여기에서 발전될 수 있는 게 스프링 시큐리티와 같은 시큐리티 컨텍스트를 통한 사용자 권한 등의 관리 방식입니다. 이는 사용자의 세션 스토어에 시큐리티 컨텍스트(저장소), 권한 정보, 인증/인가 방식, 기타 정보 등을 저장해놓아 미들웨어처럼 사용할 수 있게 해줍니다.

# OAUTH2
OAuth2는 외부 서비스의 인증 절차를 위임받아 사용하기 위한 표준 방식입니다.

`Google`, `Naver`, `Kakao`와 같은 신뢰도 있는 기업 및 서비스 등을 개발자가 만드는 서비스에 넣어 사용할 수 있는 기술을 의미합니다.

해당 방식은 앞의 방식들보다 상대적으로 복잡한 절차를 가지게 됩니다.
1. 사용자가 특정 사이트에서 `Google` 로그인 `URL`로 이동 (구글 OAuth에서 등록한 경로여야 합니다.)
2. 사용자가 GOOGLE 인증을 확인
3. 구글에서 리다이렉트 URL을 통해 나의 도메인으로 다시 이동
4. 구글에서 `authorization code` 발급
5. 내 서버가 `code`를 통해 `access token`으로 교환 (요청/응답)
6. 다음부터 해당 사용자에 대한 권한을 `access token`을 통해 호출
7. `scope`에 따른 사용자 정보 제공받기

위 방식을 통해 사용자의 인증을 다른 서비스를 통해 더 신빙성 있게 제공받을 수 있습니다.
