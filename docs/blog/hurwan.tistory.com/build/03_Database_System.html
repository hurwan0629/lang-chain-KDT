## 저장 구조
PostgreSQL을 예시로 들면 데이터베이스의 기본 페이지 크기는 일반적으로 8KB 입니다. 페이지는 row/tuple 보다 상위의 데이터이며 데이터베이스, 테이블, 물리 파일의 하위 개념으로 일반적인 cs의 페이지 개념과 같다고 볼 수 있습니다. 필요한 행이 존재하는 경우에는 해당 행만을 읽는 것이 아닌 해당 행이 들어있는 페이지 8KB를 모두 읽게됩니다.

또한 데이터베이스는 매번 디스크를 통해 읽게되면 성능이 떨어질 수 있기 때문에 페이지를 메모리에 올려두게 됩니다. PostgreSQL에서는 대표적으로 `shared_buffers`라는 메모리 공간을 사용하게 됩니다.

이에 따라 실제로 SELECT를 하는 경우, 해당 쿼리를 해결하기 위해 필요한 페이지가 무엇인지 확인하며 `shared_buffers`를 확인하여 있으면 즉시 값을 반환하여 대기시간을 줄일 수 있습니다. 여기에서 버퍼에 존재했다 라는 의미로 `Buffer Hit`, 디스크에 가야한다면 `Buffer Read` 라고 합니다.

`Dirty Page`는 메모리 안의 페이지가 수정되었지만 아직 데이터 파일에 기록되지 않은 상태를 의미합니다. 예를 들어 `update users set name = "change" where id = 10` 쿼리를 작성 시 내부 동작을 단순화하면 `users`페이지를 버퍼로 가져와 버퍼 안에서 데이터를 변경하게 됩니다. 이때 해당 버퍼 페이지가 `dirty` 상태가 되었다고 합니다. 이에 따라 나중에 변경된 페이지를 디스크에 기록하게 됩니다.

이때 `dirty`의 기준에 대해서 해당 페이지가 존재할 때 `COMMIT` 상태라고 볼 수 있는지에 대해 의문이 생길 수 있습니다. 이에 대한 정답은 COMMIT로 취급된다 입니다. (커밋 한다면)

데이터베이스에는 WAL이라는 `Write-Ahead Logging`라는 원칙을 통해 변경 전에 로그를 작업 후, COMMIT 후 실제 데이터 페이지는 나중에 기록한다는 의미를 가집니다. 이후에 변경된 페이지를 디스크에 기록하게 됩니다.

## SQL 처리 과정
SQL 한문장을 기준으로 처리되는 과정은
1. parsing: SQL 문법이 올바른지 확인 후 구조화(트리 구조로)
2. semantic analysis: 테이블, 컬럼, 타입, 문법 분석
3. rewrite: 실행 계획을 생성하게 됩니다.
4. planning: DB가 가능한 실행 방법들을 비교한다 (테이블 전체 읽기 / id 인덱스 사용 등의 선택지중 예상 비용 낮은 선택지 선택)
5. execution: 실행합니다.

## 논리적 테이블과 물리적 저장소
일반적으로 사용자가 보는 테이블은 행과 컬럼으로 이루어진 표 모양의 테이블로 보입니다. 이는 DB 내부에서 하나 이상의 물리 파일과 파일을 일정 크기의 페이지로 분할하여 각각의 페이지에 n개의 행을 저장하는 방식으로 사용하게 됩니다.

여기에서 페이지가 나오는 이유는 운영체제가 디스크와 메모리가 일반적으로 페이지로 분할하여 관리하기 때문인데 PostgreSQL의 기본 DB 페이지는 8KB의 크기를 가집니다. DB가 특정 행 하나를 읽고 싶어도 페이지에서 특정 행만 뽑아오는 것이 아닌 페이지 전체를 메모리로 가져오게 됩니다. 이렇게 가져오는 이유는 아래와 같습니다.
- 디스크 IO 호출 자체가 비싸다
- 인접한 행도 사용 가능성이 높은 지역성이 존재한다
- 고정 단위로 관리해야 캐시와 동시성 제어가 쉬워진다
- 체크섬/로그/복구도 페이지 단위로 관리하기 편하다.

이에 따라 DB 성능은 몇행을 읽었냐보다 디스크 접근 횟수. 즉, 같은 페이지를 디스크로부터 덜 가져왔냐 등이 될 수 있습니다.

## PostgreSQL 페이지 내부 구조
PostgreSQL의 일반적인 테이블 페이지는 개념적으로 페이지 앞쪽에는 행을 가리키는 `Item Pointer`과 뒤쪽에는 실제 데이터가 존재하는 `Tuple`가 저장되어있습니다.

`Item Pointer`을 따로 두는 이유는 행의 실제 바이트 위치가 페이지 내부에서 바뀌어도 외부에서는 `Item Pointer` 번호를 변경 없이 행을 쉽게 찾을 수 있는 PostgreSQL의 `CTID`가 담당하는 기능입니다.

예를 들어 `SELECT ctid, * FROM users`를 작성하면 아래와 같은 결과가 나옵니다.

| ctid | id | name |
|---|---|---|
| (0,1) | 1 | kim |
| (0,2) | 2 | hong |

이는 각각 0페이지의 1, 2번 Item Pointer 가 가리키는 행임을 나타내게 됩니다. 참고로 `CTID`는 `UPDATE`, `VACUUM FULL` 과 같은 작업으로 변경될 수 있기 때문에 `PK`같이 안정적이진 않습니다.

PostgreSQL의 한 행에는 사용자가 정의한 컬럼 외에도 내부 관리 정보가 함께 저장되는데, 
`Tuple Header`을 통해 행 버전을 만든 트랜잭션(`xmin`)과 행을 삭제하거나 무효화한 트랜잭션(`xmax`), 현재 행 버전의 물리적 위치(`ctid`), 상태 플래그, NULL 정보, 기타 메타데이터가 기본 컬럼들 외에 존재합니다.

PostgreSQL에서는 `UPDATE`가 기존 행을 그대로 바꾸는것 보다는 새로운 행 버전을 추가하는 방식에 가깝습니다. 기존에 존재하던 행에는 `xmax = 자신의 트랜잭션`을 저장해놓고 새로운 행에 `xmin = 자신의 트랜잭션`을 통해 자신이 업데이트함을 기록하게 됩니다. 여기에서 어떤 트랜잭션은 이전버전을 보고 어떤 트랜잭션은 새 버전을 보기도 합니다.

## Heap Table
PostgreSQL의 일반 테이블 저장방식을 Heap이라고 합니다. 여기에서 heap는 프로그래밍 자료구조의 최소/최대 힙과는 다르게 특정 컬럼 기준으로 정렬되어 있다는 보장이 없는 페이지의 집합을 말합니다. 이에 따라 특정 컬럼에 대한 조건 쿼리를 실행할 시 페이지를 하나씩 찾아가는 `Sequential Scan`, `Seq Scan`이 되게 됩니다.

## 테이블이 어느 페이지에 여유 공간이 있는지 찾는 방법
이전에 페이지에 `Item Pointer`과 `Tuple`가 존재한다 하였는데 데이터 행을 추가할 때마다 모든 페이지를 탐색하며 빈 공간을 찾으면 비효율적이게 됩니다. 이에 따라 PostgreSQL은 별도의 보조 정보를 사용하게 되는데 **FSM**이라는 `Free Space Map`로 각 페이지에 빈 공간이 얼마나 남았는지 관리하는 MAP 자료구조를 말합니다.

이에 따라 새 행의 크기가 들어갈 수 있는 전략에 따른 페이지를 찾게 됩니다.

**VM**은 `Visibility Map`으로 페이지 안의 모든 행이 모든 트랜잭션에게 보여지는 등의 정보를 관리하게 됩니다. 대표적으로 `Index Only Scan`과 `VACUUM` 최적화에 사용되게 됩니다. 예를 들면 1페이지는 모든 행이 visible 상태이며 2페이지는 일부 행 버전 확인이 필요하다라는 정보를 가지고 있습니다. 이를 통해 특정 페이지가 `all-visible` 상태임에 따라 테이블 페이지까지 가지 않고 인덱스만으로 결과를 낼 가능성이 생길 수 있습니다.

## 페이지보다 큰 컬럼
한 페이지가 8KB인 경우, TEXT 또는 JSON 등은 8KB보다 크기가 클 수 있습니다. 이에 따라 PostgreSQL은 TOAST를 사용하게 됩니다. 예를 들어 `POST[id: INT, content: TEXT]`가 존재한다 하면 `POST.content`에는 TOAST 데이터에 대한 참조가 저장되어 `TOAST` 테이블에서 긴 데이터를 여러 조각으로 나누어 저장할 수 있게 됩니다.

> 한 행 전체가 반드시 하나의 데이터 페이지 안에 원래 모습 그대로 들어가는 것은 아닙니다. 

## dirty page
위에서 언급하였듯 PostgreSQL은 디스크에서 페이지 단위로 데이터를 가져와 사용하게 되는데 데이터를 수정하는 경우, 테이블 페이지를 `shared_buffer`에서 수정한 뒤 적절한 시점에 여러 COMMIT된 `dirty page`를 기록하게 됩니다.

## WAL
WAL은 수정된 데이터 페이지를 디스크에 쓰기 전에, 그 변경을 복구할 수 있는 로그를 먼저 안전하게 기록하는 기능입니다. 예를 들어 `users`페이지에서 `id=1` 행의 새 버전을 생성하였다는 정보를 WAL에 기록하며 WAL을 먼저 디스크에 flush한 뒤 클라이언트에게 COMMIT 성공 응답을 하게 됩니다. 이후 COMMIT 된 dirty page는 적절한 때에 데이터 파일에 기록하게 됩니다. 이를 통해 COMMIT 뒤 서버가 죽어도 이전 페이지 WAL에 변경 성공 기록을 보고 변경을 다시 적용할 수 있게 됩니다.

## Dirty Page를 쓰는 주체
- Checkpointer: 체크포인트 시점에 필요한 dirty page를 데이터 파일에 반영합니다.
- Background Writer: 백그라운드에서 일부 dirty buffer을 미리 기록해서 사용자가 직접 페이지를 써야하는 상황을 줄이게 합니다.
- Backend Process: 새 페이지를 읽어야하는데 교체할 버퍼가 dirty하다면 실제 쿼리를 처리하는 프로세스가 직접 디스크에 기록하기도 합니다.

## UPDATE 한건의 생명 주기
`BEGIN`, `UPDATE users SET name = 'hurwan' WHERE id = 1`, `COMMIT`가 이루어져 있을 때, 기존 데이터 `name: kim, id: 1`이 바뀐게 됩니다.

먼저 PostgreSQL 실행기가 `id=1`인 행을 찾게 됩니다. 여기에서 Heap 페이지 번호와 Item Pointer을 확인하게 됩니다. `shared_buffers`에서 Heap 페이지를 확인합니다.

여기에서 인덱스가 존재하지 않을 경우에는 Heap 페이지를 순서대로 읽어 페이지 내부 Tuple을 검사하게 됩니다.

또한 페이지가 `shared_buffers`(디스크/OS 캐시)에 존재하지 않으면 디스크로부터 데이터를 읽어오게 됩니다.

이후 Tuple Header을 본 뒤 해당 행이 현재 트랜잭션의 스냅샷에서 보이는지 판단하게 됩니다. 여기에서 이전버전을 만든 정보가 존재하며 아직 삭제되거나 대체되었다는 `xmax`가 존재하지 않으면 데이터가 쓰이지 않고 있음을 알 수 있습니다.

이후 다른 트랜잭션과의 충돌을 피하기 위해 확인 후 기다리거나 실패하게 됩니다. 예를 들어 첫번째 트랜잭션이 `id=1`을 작업중일 시 다른 작업이 해당 행을 수정하려하면 앞선 작업의 COMMIT 후 다시 판단을 하거나 앞선 작업의 ROLLBACK 후 다음 작업이 그대로 일어날 수 있습니다.

## 설정에 따른 격리수준
이전에도 다뤄보긴 했었지만 PostgreSQL의 기본값인 `READ COMMITTED`는 한 트랜잭션에서 첫번째 `SELECT`에서 `id=1, name="hur"`을 봤었는데 자신의 트랜잭션이 끝나기 전 다른 트랜잭션의 `COMMIT`으로 인해 `id=1, name="kim"`이 되었다면 이는 같은 트랜잭션에서 스냅샷 없이 그대로 `kim`으로 읽어져 한 트랜잭션의 같은 SELECT에서 다른 결과가 나올 수 있습니다.

반대로 `REPEATABLE READ`인 경우에는 같은 스냅샷을 유지하게 됩니다.

`SERIALIZABLE`는 스냅샷 뿐 아니라 직렬화 불가능한 의존성까지 검사하게 됩니다.

여기에서 스냅샷은 `xmin`, `xmax`, `xip_list`로 트랜잭션 `XID`가 `xmin`보다 작으면 종료된 트랜잭션이며 `xmin`과 `xmax` 사이는 해당 지점 사이에서 실행중이며 `xmax`보다 큰 경우에는 해당 `xmin`, `xmax`에 대한 튜플이 보이지 않게 됩니다. 

## 트랜잭션의 성패 관리
PostgreSQL에서 쓰기 작업을 시작한 트랜잭션을 전역적으로 `XID`를 받게 됩니다. 이는 처음으로 DB에 쓰기작업을 할 때 (BEGIN 타이밍과 다름) 할당받는 트랜잭션의 고유한 아이디입니다.

트랜잭션은 개념적으로 다음과 같은 상태를 가지게 됩니다.
- `in progress`
- `committed`
- `aborted`

PostgreSQL의 최근 트랜잭션의 최종 상태는 `pg_xact`라는 별도 영역에서 관리되며 `pg_xact_status()`를 통해 해당 XID가 실행중인지, 커밋되었는지, 중단되었는지 확인하게 됩니다.

이를 통해 Tuple에 기록된 `xmin` 정보 또는 `xmax`정보와 `pg_xact`를 활용하여 해당 튜플에 대한 커밋 여부를 확인할 수 있게 됩니다.

이러한 여러 버전을 존재시키면서 동시성을 관리하는 방식을 MVCC라고 부릅니다.

여기에서 이제 `xmax=0`인 튜플이 생성된 뒤 이전 버전을 참조하던 모든 트랜잭션 작업이 끝나게 된다면 해당 튜플은 Dead Tuple로써 `VACUUM`이라는 불필요한 행 버전의 공간을 재사용할 수 있게 만들어줍니다.

## 락
MVCC를 통해 읽기와 쓰기가 서로 불필요하게 막히지 않게끔 읽기와 쓰기를 분리할 수 있지만 같은 행을 동시에 수정하는 경우에 둘 다 새 버전을 만들게 동시에 허락할 수 없습니다. 이에 따라 행 수준 충돌제어가 제공되는데 이는 일반 SELECT를 막기보다는 같은 행의 수정이나 잠금 작업을 막아주게 됩니다.

여기에서 데드락의 경우에는 이러한 대기상태가 다른 트랜잭션에서 서로의 자원에 대한 해제를 기다리는 교착상황을 이야기합니다. 예를 들어 100번 트랜잭션은 `id=5`행을 가지고 `id=10`을 기다리고 101번 트랜잭션은 `id=10`을 가지고 `id=5`행을 기다리는 형태입니다.

이렇게 PostgreSQL은 이런 순환을 감지하면 관련 트랜잭션 중 하나를 중단시켜 나머지가 진행되도록 하게 합니다.

PostgreSQL에 적용되는 방지기법 중에는 자원을 점유(락을 거는)하는 순서를 정렬하여 서로 순환되지 않게 하는 방법이 있기도 합니다.

## 실행 계획
옵티마이저는 고정된 규칙으로 인덱스가 있으면 사용하는 것이 아닙니다. 가능한 실행 방법들을 생성 후 그중 가장 적은 비용으로 실행 가능한 실행을 하게 됩니다. 항상 `Seq Scan`이라는 페이지를 순서대로 읽는 방식, 조건과 맞는 인덱스가 있으면 `Index Scan`등과 같은 후보가 추가됩니다. `JOIN`에 따라서 `Nested Loop`(중첩 루프), `Hash Join`(작은 테이블에 해싱 후 다른 테이블 선형 탐색), `Merge Join`(조인컬럼 정렬 후 조합)등이 추가될 수 있습니다.

주로 판단의 근거가 되는 것들은
- 테이블 페이지 수
- 전체 행 수
- 조건에 맞을 것으로 예상되는 행 수
- 값의 분포와 중복도
- 인덱스 존재 여부
- 디스크 페이지 접근 비용
- cpu 조건 검사
- 정렬 필요
- 사용 가능 메모리 등

위의 정보는 대체로 `ANALYZE`가 수집한 통계에서 나오게 됩니다.

경우에 따라 
- 아주 적은 행: Index Scan 실행 가능
- 일부 페이지에 흩어진 여러 행: `Bitmap Index Scan`으로 튜플 위치 모아 `Bitmap Heap Scan`으로 페이지 접근
- 전체 행의 대부분이 조건에 충족되면: 순차적으로 읽는 것이 더 저렴할 수 있음

등과 같은 판단이 일어날 수 있습니다.

DB 엔진

데이터베이스 엔진은 일반적으로 서버의 형태로 요청에 대한 SQL을 파싱, 분석, 실행계획 및 실행 후 여러 작업을 거쳐 최종적으로 기존의 데이터를 보존하며 결과를 제공 하거나 요청에 따라 무결성을 지키며 데이터를 변형해줍니다.

저장 구조

PostgreSQL을 예시로 들면 데이터베이스의 기본 페이지 크기는 일반적으로 8KB 입니다. 페이지는 row/tuple 보다 상위의 데이터이며 데이터베이스, 테이블, 물리 파일의 하위 개념으로 일반적인 cs의 페이지 개념과 같다고 볼 수 있습니다. 필요한 행이 존재하는 경우에는 해당 행만을 읽는 것이 아닌 해당 행이 들어있는 페이지 8KB를 모두 읽게됩니다.

또한 데이터베이스는 매번 디스크를 통해 읽게되면 성능이 떨어질 수 있기 때문에 페이지를 메모리에 올려두게 됩니다. PostgreSQL에서는 대표적으로 shared_buffers라는 메모리 공간을 사용하게 됩니다.

이에 따라 실제로 SELECT를 하는 경우, 해당 쿼리를 해결하기 위해 필요한 페이지가 무엇인지 확인하며 shared_buffers를 확인하여 있으면 즉시 값을 반환하여 대기시간을 줄일 수 있습니다. 여기에서 버퍼에 존재했다 라는 의미로 Buffer Hit, 디스크에 가야한다면 Buffer Read 라고 합니다.

Dirty Page는 메모리 안의 페이지가 수정되었지만 아직 데이터 파일에 기록되지 않은 상태를 의미합니다. 예를 들어 update users set name = "change" where id = 10 쿼리를 작성 시 내부 동작을 단순화하면 users페이지를 버퍼로 가져와 버퍼 안에서 데이터를 변경하게 됩니다. 이때 해당 버퍼 페이지가 dirty 상태가 되었다고 합니다. 이에 따라 나중에 변경된 페이지를 디스크에 기록하게 됩니다.

이때 dirty의 기준에 대해서 해당 페이지가 존재할 때 COMMIT 상태라고 볼 수 있는지에 대해 의문이 생길 수 있습니다. 이에 대한 정답은 COMMIT로 취급된다 입니다. (커밋 한다면)

데이터베이스에는 WAL이라는 Write-Ahead Logging라는 원칙을 통해 변경 전에 로그를 작업 후, COMMIT 후 실제 데이터 페이지는 나중에 기록한다는 의미를 가집니다. 이후에 변경된 페이지를 디스크에 기록하게 됩니다.

SQL 처리 과정

SQL 한문장을 기준으로 처리되는 과정은

  1. parsing: SQL 문법이 올바른지 확인 후 구조화(트리 구조로)
  2. semantic analysis: 테이블, 컬럼, 타입, 문법 분석
  3. rewrite: 실행 계획을 생성하게 됩니다.
  4. planning: DB가 가능한 실행 방법들을 비교한다 (테이블 전체 읽기 / id 인덱스 사용 등의 선택지중 예상 비용 낮은 선택지 선택)
  5. execution: 실행합니다.

논리적 테이블과 물리적 저장소

일반적으로 사용자가 보는 테이블은 행과 컬럼으로 이루어진 표 모양의 테이블로 보입니다. 이는 DB 내부에서 하나 이상의 물리 파일과 파일을 일정 크기의 페이지로 분할하여 각각의 페이지에 n개의 행을 저장하는 방식으로 사용하게 됩니다.

여기에서 페이지가 나오는 이유는 운영체제가 디스크와 메모리가 일반적으로 페이지로 분할하여 관리하기 때문인데 PostgreSQL의 기본 DB 페이지는 8KB의 크기를 가집니다. DB가 특정 행 하나를 읽고 싶어도 페이지에서 특정 행만 뽑아오는 것이 아닌 페이지 전체를 메모리로 가져오게 됩니다. 이렇게 가져오는 이유는 아래와 같습니다.

  • 디스크 IO 호출 자체가 비싸다
  • 인접한 행도 사용 가능성이 높은 지역성이 존재한다
  • 고정 단위로 관리해야 캐시와 동시성 제어가 쉬워진다
  • 체크섬/로그/복구도 페이지 단위로 관리하기 편하다.

이에 따라 DB 성능은 몇행을 읽었냐보다 디스크 접근 횟수. 즉, 같은 페이지를 디스크로부터 덜 가져왔냐 등이 될 수 있습니다.

PostgreSQL의 테이블과

PostgreSQL 페이지 내부 구조

PostgreSQL의 일반적인 테이블 페이지는 개념적으로 페이지 앞쪽에는 행을 가리키는 Item Pointer과 뒤쪽에는 실제 데이터가 존재하는 Tuple가 저장되어있습니다.

Item Pointer을 따로 두는 이유는 행의 실제 바이트 위치가 페이지 내부에서 바뀌어도 외부에서는 Item Pointer 번호를 변경 없이 행을 쉽게 찾을 수 있는 PostgreSQL의 CTID가 담당하는 기능입니다.

예를 들어 SELECT ctid, * FROM users를 작성하면 아래와 같은 결과가 나옵니다.

ctididname
(0,1)1kim
(0,2)2hong

이는 각각 0페이지의 1, 2번 Item Pointer 가 가리키는 행임을 나타내게 됩니다. 참고로 CTID는 UPDATE, VACUUM FULL 과 같은 작업으로 변경될 수 있기 때문에 PK같이 안정적이진 않습니다.

PostgreSQL의 한 행에는 사용자가 정의한 컬럼 외에도 내부 관리 정보가 함께 저장되는데, Tuple Header을 통해 행 버전을 만든 트랜잭션(xmin)과 행을 삭제하거나 무효화한 트랜잭션(xmax), 현재 행 버전의 물리적 위치(ctid), 상태 플래그, NULL 정보, 기타 메타데이터가 기본 컬럼들 외에 존재합니다.

PostgreSQL에서는 UPDATE가 기존 행을 그대로 바꾸는것 보다는 새로운 행 버전을 추가하는 방식에 가깝습니다. 기존에 존재하던 행에는 xmax = 자신의 트랜잭션을 저장해놓고 새로운 행에 xmin = 자신의 트랜잭션을 통해 자신이 업데이트함을 기록하게 됩니다. 여기에서 어떤 트랜잭션은 이전버전을 보고 어떤 트랜잭션은 새 버전을 보기도 합니다.

Heap Table

PostgreSQL의 일반 테이블 저장방식을 Heap이라고 합니다. 여기에서 heap는 프로그래밍 자료구조의 최소/최대 힙과는 다르게 특정 컬럼 기준으로 정렬되어 있다는 보장이 없는 페이지의 집합을 말합니다. 이에 따라 특정 컬럼에 대한 조건 쿼리를 실행할 시 페이지를 하나씩 찾아가는 Sequential Scan, Seq Scan이 되게 됩니다.

테이블이 어느 페이지에 여유 공간이 있는지 찾는 방법

이전에 페이지에 Item Pointer과 Tuple가 존재한다 하였는데 데이터 행을 추가할 때마다 모든 페이지를 탐색하며 빈 공간을 찾으면 비효율적이게 됩니다. 이에 따라 PostgreSQL은 별도의 보조 정보를 사용하게 되는데 **FSM**이라는 Free Space Map로 각 페이지에 빈 공간이 얼마나 남았는지 관리하는 MAP 자료구조를 말합니다.

이에 따라 새 행의 크기가 들어갈 수 있는 전략에 따른 페이지를 찾게 됩니다.

**VM**은 Visibility Map으로 페이지 안의 모든 행이 모든 트랜잭션에게 보여지는 등의 정보를 관리하게 됩니다. 대표적으로 Index Only Scan과 VACUUM 최적화에 사용되게 됩니다. 예를 들면 1페이지는 모든 행이 visible 상태이며 2페이지는 일부 행 버전 확인이 필요하다라는 정보를 가지고 있습니다. 이를 통해 특정 페이지가 all-visible 상태임에 따라 테이블 페이지까지 가지 않고 인덱스만으로 결과를 낼 가능성이 생길 수 있습니다.

페이지보다 큰 컬럼

한 페이지가 8KB인 경우, TEXT 또는 JSON 등은 8KB보다 크기가 클 수 있습니다. 이에 따라 PostgreSQL은 TOAST를 사용하게 됩니다. 예를 들어 POST[id: INT, content: TEXT]가 존재한다 하면 POST.content에는 TOAST 데이터에 대한 참조가 저장되어 TOAST 테이블에서 긴 데이터를 여러 조각으로 나누어 저장할 수 있게 됩니다.

한 행 전체가 반드시 하나의 데이터 페이지 안에 원래 모습 그대로 들어가는 것은 아닙니다.

dirty page

위에서 언급하였듯 PostgreSQL은 디스크에서 페이지 단위로 데이터를 가져와 사용하게 되는데 데이터를 수정하는 경우, 테이블 페이지를 shared_buffer에서 수정한 뒤 적절한 시점에 여러 COMMIT된 dirty page를 기록하게 됩니다.

WAL

WAL은 수정된 데이터 페이지를 디스크에 쓰기 전에, 그 변경을 복구할 수 있는 로그를 먼저 안전하게 기록하는 기능입니다. 예를 들어 users페이지에서 id=1 행의 새 버전을 생성하였다는 정보를 WAL에 기록하며 WAL을 먼저 디스크에 flush한 뒤 클라이언트에게 COMMIT 성공 응답을 하게 됩니다. 이후 COMMIT 된 dirty page는 적절한 때에 데이터 파일에 기록하게 됩니다. 이를 통해 COMMIT 뒤 서버가 죽어도 이전 페이지 WAL에 변경 성공 기록을 보고 변경을 다시 적용할 수 있게 됩니다.

Dirty Page를 쓰는 주체

  • Checkpointer: 체크포인트 시점에 필요한 dirty page를 데이터 파일에 반영합니다.
  • Background Writer: 백그라운드에서 일부 dirty buffer을 미리 기록해서 사용자가 직접 페이지를 써야하는 상황을 줄이게 합니다.
  • Backend Process: 새 페이지를 읽어야하는데 교체할 버퍼가 dirty하다면 실제 쿼리를 처리하는 프로세스가 직접 디스크에 기록하기도 합니다.

UPDATE 한건의 생명 주기

BEGIN, UPDATE users SET name = 'hurwan' WHERE id = 1, COMMIT가 이루어져 있을 때, 기존 데이터 name: kim, id: 1이 바뀐게 됩니다.

먼저 PostgreSQL 실행기가 id=1인 행을 찾게 됩니다. 여기에서 Heap 페이지 번호와 Item Pointer을 확인하게 됩니다. shared_buffers에서 Heap 페이지를 확인합니다.

여기에서 인덱스가 존재하지 않을 경우에는 Heap 페이지를 순서대로 읽어 페이지 내부 Tuple을 검사하게 됩니다.

또한 페이지가 shared_buffers(디스크/OS 캐시)에 존재하지 않으면 디스크로부터 데이터를 읽어오게 됩니다.

이후 Tuple Header을 본 뒤 해당 행이 현재 트랜잭션의 스냅샷에서 보이는지 판단하게 됩니다. 여기에서 이전버전을 만든 정보가 존재하며 아직 삭제되거나 대체되었다는 xmax가 존재하지 않으면 데이터가 쓰이지 않고 있음을 알 수 있습니다.

이후 다른 트랜잭션과의 충돌을 피하기 위해 확인 후 기다리거나 실패하게 됩니다. 예를 들어 첫번째 트랜잭션이 id=1을 작업중일 시 다른 작업이 해당 행을 수정하려하면 앞선 작업의 COMMIT 후 다시 판단을 하거나 앞선 작업의 ROLLBACK 후 다음 작업이 그대로 일어날 수 있습니다.

설정에 따른 격리수준

이전에도 다뤄보긴 했었지만 PostgreSQL의 기본값인 READ COMMITTED는 한 트랜잭션에서 첫번째 SELECT에서 id=1, name="hur"을 봤었는데 자신의 트랜잭션이 끝나기 전 다른 트랜잭션의 COMMIT으로 인해 id=1, name="kim"이 되었다면 이는 같은 트랜잭션에서 스냅샷 없이 그대로 kim으로 읽어져 한 트랜잭션의 같은 SELECT에서 다른 결과가 나올 수 있습니다.

반대로 REPEATABLE READ인 경우에는 같은 스냅샷을 유지하게 됩니다.

SERIALIZABLE는 스냅샷 뿐 아니라 직렬화 불가능한 의존성까지 검사하게 됩니다.

여기에서 스냅샷은 xmin, xmax, xip_list로 트랜잭션 XID가 xmin보다 작으면 종료된 트랜잭션이며 xmin과 xmax 사이는 해당 지점 사이에서 실행중이며 xmax보다 큰 경우에는 해당 xmin, xmax에 대한 튜플이 보이지 않게 됩니다.

트랜잭션의 성패 관리

PostgreSQL에서 쓰기 작업을 시작한 트랜잭션을 전역적으로 XID를 받게 됩니다. 이는 처음으로 DB에 쓰기작업을 할 때 (BEGIN 타이밍과 다름) 할당받는 트랜잭션의 고유한 아이디입니다.

트랜잭션은 개념적으로 다음과 같은 상태를 가지게 됩니다.

  • in progress
  • committed
  • aborted

PostgreSQL의 최근 트랜잭션의 최종 상태는 pg_xact라는 별도 영역에서 관리되며 pg_xact_status()를 통해 해당 XID가 실행중인지, 커밋되었는지, 중단되었는지 확인하게 됩니다.

이를 통해 Tuple에 기록된 xmin 정보 또는 xmax정보와 pg_xact를 활용하여 해당 튜플에 대한 커밋 여부를 확인할 수 있게 됩니다.

이러한 여러 버전을 존재시키면서 동시성을 관리하는 방식을 MVCC라고 부릅니다.

여기에서 이제 xmax=0인 튜플이 생성된 뒤 이전 버전을 참조하던 모든 트랜잭션 작업이 끝나게 된다면 해당 튜플은 Dead Tuple로써 VACUUM이라는 불필요한 행 버전의 공간을 재사용할 수 있게 만들어줍니다.

락

MVCC를 통해 읽기와 쓰기가 서로 불필요하게 막히지 않게끔 읽기와 쓰기를 분리할 수 있지만 같은 행을 동시에 수정하는 경우에 둘 다 새 버전을 만들게 동시에 허락할 수 없습니다. 이에 따라 행 수준 충돌제어가 제공되는데 이는 일반 SELECT를 막기보다는 같은 행의 수정이나 잠금 작업을 막아주게 됩니다.

여기에서 데드락의 경우에는 이러한 대기상태가 다른 트랜잭션에서 서로의 자원에 대한 해제를 기다리는 교착상황을 이야기합니다. 예를 들어 100번 트랜잭션은 id=5행을 가지고 id=10을 기다리고 101번 트랜잭션은 id=10을 가지고 id=5행을 기다리는 형태입니다.

이렇게 PostgreSQL은 이런 순환을 감지하면 관련 트랜잭션 중 하나를 중단시켜 나머지가 진행되도록 하게 합니다.

PostgreSQL에 적용되는 방지기법 중에는 자원을 점유(락을 거는)하는 순서를 정렬하여 서로 순환되지 않게 하는 방법이 있기도 합니다.

실행 계획

옵티마이저는 고정된 규칙으로 인덱스가 있으면 사용하는 것이 아닙니다. 가능한 실행 방법들을 생성 후 그중 가장 적은 비용으로 실행 가능한 실행을 하게 됩니다. 항상 Seq Scan이라는 페이지를 순서대로 읽는 방식, 조건과 맞는 인덱스가 있으면 Index Scan등과 같은 후보가 추가됩니다. JOIN에 따라서 Nested Loop(중첩 루프), Hash Join(작은 테이블에 해싱 후 다른 테이블 선형 탐색), Merge Join(조인컬럼 정렬 후 조합)등이 추가될 수 있습니다.

주로 판단의 근거가 되는 것들은

  • 테이블 페이지 수
  • 전체 행 수
  • 조건에 맞을 것으로 예상되는 행 수
  • 값의 분포와 중복도
  • 인덱스 존재 여부
  • 디스크 페이지 접근 비용
  • cpu 조건 검사
  • 정렬 필요
  • 사용 가능 메모리 등

위의 정보는 대체로 ANALYZE가 수집한 통계에서 나오게 됩니다.

경우에 따라

  • 아주 적은 행: Index Scan 실행 가능
  • 일부 페이지에 흩어진 여러 행: Bitmap Index Scan으로 튜플 위치 모아 Bitmap Heap Scan으로 페이지 접근
  • 전체 행의 대부분이 조건에 충족되면: 순차적으로 읽는 것이 더 저렴할 수 있음

등과 같은 판단이 일어날 수 있습니다.
