# Blog HTML 작업 지침

이 폴더는 티스토리에 업로드할 학습 글을 HTML 형태로 정리하는 작업 공간이다. 다음 작업에서도 아래 방식을 유지한다.

## 핵심 원칙

- 사용자가 작성한 원문 내용은 임의로 쉽게 풀어쓰거나 요약하지 않는다.
- GPT의 역할은 내용 변경이 아니라 가독성, 서식, 시각적 일관성 개선이다.
- 치명적인 기술 오류, 오탈자, 서식 깨짐, 가독성을 해치는 표현이 있으면 먼저 조언한다.
- 사용자가 명시적으로 요청하기 전에는 원문 파일을 직접 수정하지 않는다.
- 원본 HTML이 있으면 덮어쓰지 말고 `update_*.html` 또는 새 번호 HTML을 만든다.

## 작업 흐름

1. 새 `.md` 또는 `.html` 파일을 받으면 먼저 읽고 검토한다.
2. 기술적으로 치명적인 오류나 렌더링을 깨는 서식 문제가 있으면 HTML 생성 전에 사용자에게 알린다.
3. 문제가 없거나 사용자가 진행을 요청하면 기존 스타일을 재사용해 HTML을 만든다.
4. 작업 후에는 파일 생성 여부, 핵심 구조, 토글 위치, 목차, 섹션 id, 인라인 코드 스타일을 확인한다.

## 스타일 기준

- 전체 래퍼는 `.tech-post`를 사용한다.
- 기본 톤은 흰 배경, 초록 포인트 컬러(`#19b97c`), 밝은 카드형 레이아웃을 유지한다.
- 글 상단에는 `.post-hero`를 사용하고, `post-kicker`, `post-title`, `post-subtitle` 구조를 둔다.
- 목차는 `.post-toc`으로 만들고, 각 섹션은 `section-01`, `section-02` 같은 id를 가진다.
- 본문 섹션은 `.post-section`, 카드형 설명은 `.post-card.stack`을 사용한다.
- 강조 노트는 `.post-note`를 사용한다.
- 표는 `.read-table`을 사용한다.
- 코드 블록 또는 계산 예시는 `.output-box` 또는 `.code-box`를 사용한다.
- 일반 본문 문단은 너무 얇어 보이지 않도록 `font-weight: 500`, `color: #334155` 기준을 유지한다.

## 인라인 코드 처리

- 본문 중 `a = "hello"`, `.py`, `co_code`, `int`, `float`, `globals()` 같은 짧은 코드/기호 표현은 `<code>`로 감싼다.
- 인라인 `<code>`는 밝은 회색 배경(`#f1f5f9`)과 작은 border를 적용한다.
- 코드 블록의 `<pre><code>...</code></pre>`에는 인라인 코드 스타일이 덮어씌워지지 않게 한다.
- 마크다운 백틱이 HTML 본문에 그대로 남지 않도록 필요한 경우 `<code>`로 바꾼다.

## 원본 토글

- 사용자가 원문 확인을 원하면 글 상단, hero 아래에 `<details class="source-toggle">`를 추가한다.
- 첫 번째 원본 토글 제목은 사용자가 별도 지정하지 않으면 `gpt가 디자인 하기 전 원본`을 사용한다.
- 추가 학습 메모나 부록은 원본 토글 아래에 별도 토글로 추가한다.
- 예: `<summary>일부 내용 보강 학습</summary>`
- 토글 안에는 원문을 최대한 그대로 보존한다.
- 토글 내부의 원문은 `<pre class="source-box"><code>...</code></pre>` 형태로 넣는다.
- HTML에서 깨질 수 있는 `&`, `<`, `>`, `->` 등은 표시가 유지되도록 이스케이프한다.

## 내용 검토 기준

HTML 생성 전 다음을 확인한다.

- 마크다운 코드블록 ```가 열리고 닫혔는지 확인한다.
- 표가 코드블록 안에 들어가 있으면 일반 표 렌더링이 필요한지 확인한다.
- 기술 오류가 있으면 사용자에게 조언한다.
- 확실하지 않은 기술 사실은 단정하지 말고 재확인이 필요하다고 말한다.
- 오탈자는 발견해도 사용자가 요청하지 않으면 원문을 고치지 않는다.

## 이번 작업에서 특히 확인했던 유형

- 1의 보수에서 8비트 `+0`은 `0000 0000`, `-0`은 `1111 1111`이다.
- 8비트 2의 보수 범위는 `-128`~`127`이다.
- 부동소수점 오차는 2의 보수 문제가 아니라 2진 소수 표현과 IEEE 754 표현 한계로 설명한다.
- CPU는 보통 변수 타입을 직접 아는 것이 아니라, 컴파일러/인터프리터/런타임이 타입에 맞는 명령어와 해석 방식을 선택한다.
- `Decimal`, `coefficient`, IEEE 754 지수 범위 같은 용어는 오탈자나 범위 오류가 생기기 쉬우므로 조언 대상으로 본다.

## 파일 생성 규칙

- 기존 번호 HTML을 직접 덮어쓰지 않는다.
- 기존 글 개선본은 `update_1.html`, `update_2.html`처럼 만든다.
- 새 글은 다음 번호의 HTML 파일로 만든다.
- 생성 후에는 `Get-ChildItem`과 `Select-String` 등으로 파일 존재, 토글, 목차, 섹션, 닫는 태그를 확인한다.
