# `프론트 기술`
## 렌더링의 종류
- SSG: 정적 사이트 생성으로 순수 `.html`, `.php` 파일과 같은 순수 문서 형태로 저장됩니다. 서버/클라이언트의 큰 부담이 없지만 데이터가 
- ISR: 점진적 정적 생성으로 `SSG`와 동일하지만 일정 주기를 기준으로 파일을 캐싱하여 보내는 방식입니다.
- SPA: 싱글 페이지 어플리케이션으로 사용자에게 어플리케이션 프론트 데이터 전체를 한번에 주어 사용자가 url 이동 없이도 js 렌더링을 통해 프론트를 구현하는 방식 (초기 로딩 느리고 검색엔진에 잘 안걸려서 홍보효과 낮음)
- MPA: 여러 페이지를 만들어두는 방식으로 SPA와 반대 방식
- SSR: 서버쪽에서 미리 렌더링하여 데이터를 주는 방식으로 서버가 부담이 되는 형태
- CSR: 클라이언트에게 `html`만 준다음에 클라이언트가 필요에 따라 `js` 파일을 요청하여 페이지를 렌더링 하는 방식
## 프론트 라이브러리
- React: 상태 기반의 JavaScript 및 컴포넌트를 통해 UI를 생성한다.
- Vue: HTML 에 JS 표현식을 넣어 표현식 기반의 컴퓨넌트를 만든다.
## 프론트 프레임워크의 종류
- Next: 리액트 기반의 js/ts 풀스택 프레임워크. SSR, SPA, CSR, MPA(부분), SSG, ISR 모두 사용 가능. 백엔드의 역할 또한 할 수 있으며 노드서버 기반으로 싱글 스레드 비동기 처리 작업에 강함.(CPU/GPU 작업에 약함) 즉 프론트 개발용으로는 강력하지만 AI, 세션유지, 백엔드 역할/책임 구조, 장시간 대기, 큰 데이터 처리 등에 약하기 때문에 
- Nuxt: 이 또한 Next와 다른 UI 라이브러리(Vue)를 사용한다는 점 이외에는 동일한 특징을 가지고 있음. (문법이 다르다고 보면 됨.) 
## 개발 서버 및 빌드 도구
- Vite: 개발 서버(최적화된 노드몬 느낌) 및 여러 프레임워크 및 UI 라이브러리를 배포 가능한 `html` `css` `js` 형태로 만들어줌

## `서버의 구조`
> `Node`서버(Express, Nest 등)는 애초에 싱글스레드기반이라 제외, `Spring`는 배우지 않았으니 `python`만을 이용하여 이야기 하도록 하겠습니다.

파이썬 프레임워크는 크게 3가지가 존재합니다.
- Flask: 마이크로 프레임워크로 최소기능만 제공하여 인증, api문서, 비동기처리에 약하여 실서비스에는 어려움.
- Django: 웹 풀스택 프레임워크. ORM을 제공하며 관리자페이지 기본 제공, 인증인가도 기본으로 제공함. 비동기를 제공하긴 하지만 전통적으로 동기 중심
- FastAPI: 타입 힌트 기반의 API개발이 가능하며 보통 비동기 API 서버를 위해 동작함. 비동기에 강력하며 ORM은 SQLAlchemty 등과 같은 다른 라이브러리를 사용해야함.

### 서버의 선택
서버를 선택하는 경우, `Flask`는 애초에 실제 본격적으로 배포하기 위한 서비스가 아니기에 제외하며, `Next`를 통해 프론트를 맡기 때문에 강한 풀스택 프레임워크는 필요하지 않음. 따라서 선택적 `ORM` 및 강한 비동기 기능(싱글 스레드 기반의), 워커 관리 등의 면에서 `FastAPI`가 더 유리한 느낌이 강합니다. (웹 서비스를 강하게 한다면 그때 `Django`를 추가해도 늦지 않습니다.)

### 결론
> 기본적으로 `FastAPI`를 채택하는 것이 AI 서비스에 가장 잘 맞습니다. 규모가 커지면 `Django`를 추가하면 됩니다.

## `워커`
워커는 별도로 실행되는 프로세스 또는 컨테이너에 가깝습니다. 앞에서 설명한 프론트서버, 백엔드서버와 다르게 특정 작업(우리는 주로 AI 추론 작업)을 하는데 사용됩니다. 만일 모델 자체가 추론에 계산이 많이 들어가지 않는 경우에는 워커를 사용하지 않을 수 있습니다.

워커를 사용하는 경우에는 기존에 존재하던 백엔드 서버(FastAPI 같은) 이외에 추가해야할 요소가
- 워커: 실질적으로 CPU를 사용하며 요청한 작업을 하는 요소 (보통 컨테이너 등과 같은 것으로 필요에 따라 수를 조절하는 방식)
- 브로커: 워커가 수행할 작업을 올려두는 메시지 큐 (보통 Redis같은 캐싱 서버를 이용하는데 이는 다른 용도로도 함께 쓰일 수 있습니다. 아니면 메시지큐 특화 RabbitMQ를 사용 가능합니다. 더 규모가 큰 경우에는 Kafka를 사용할 수 있습니다.)
- 데이터베이스: 워커가 끝낸 데이터를 넣는 공간이 됩니다. (기존에 사용하던 데이터베이스를 그대로 사용할 수 있습니다.)

### 워커를 사용할 때 유의할점
워커를 사용할 때 서버 개수가 늘어버린다던가 개발 작업이 많아지는 것은 상대적으로 큰 문제는 아닙니다. 하지만 이를 설계할 때 예외에 대해서 처리해야하는 경우가 많기 때문에 이에 대해서 유의를 할 필요가 있습니다. 예를 들면 다음과 같은 경우가 존재할 수 있습니다.
- 작업 실패
- 재시도
- 중복실행 방지
- 타임아웃 설정
- 워커가 죽었을 때 복구
- 로그 추적
- 큐 작업량 모니터링

> 워커는 실제로 CPU를 활용하기 때문에 이는 비용에 큰 영향을 끼칠 수 있는 요소입니다. 따라서 가능한 모델 자체를 학습 이후 추론 과정에 CPU를 덜 사용하게 하는것이 좋습니다.
